# M18: Independent evaluator, portable across CLIs — Implementation Plan

**Goal:** A separate, read-only evaluator agent judges each opted-in
feature before it can flip to `passing`, in Claude Code, Codex CLI and
Copilot CLI alike. One evaluator covers three jobs: review (always),
QA (when `evaluate: "ui"`), and a security checklist (when the feature's
`paths` touch sensitive areas). Released as plugin 1.9.0.

**Why:** Today the session that builds a feature also writes its verify,
runs the gate and flips its own status — it grades its own homework. A
green gate proves the tests pass, not that they test the right thing.
Stubbed, display-only, or API-works-but-UI-broken features slip through.

## M18-001 — Neutral agent sources and a per-CLI generator

- Two neutral role files: `agents/src/harness-builder.md` (full tools,
  standard tier) and `agents/src/harness-evaluator.md` (read-only,
  standard tier).
- `scripts/gen-agents.sh <target-repo>` emits, from those sources:
  - `.claude/agents/<name>.md` (Claude Code)
  - `.github/agents/<name>.agent.md` (Copilot CLI; `description`
    required, `model` a single string)
  - `.codex/agents/<name>.toml` (Codex; evaluator gets
    `sandbox_mode = "read-only"`)
- File name == `name` field in every format (Copilot's `--agent` uses
  the file name). Model tier → model name comes from
  `agents/models.json` (cheap / standard / strong per CLI).
- Evaluator prompt contract: input is only the feature entry, the commit
  range and its `bar`; never the builder's transcript. Observe before
  judging (run the app or the named check). First line exactly `PASS`
  or `NEEDS_WORK`, then numbered findings with file:line or repro steps.
  Skeptical default: stubs, display-only controls and API-only features
  are NEEDS_WORK.
- Gate (scripts/test-agents.sh): generator output exists for all three
  CLIs; evaluator tool lists exclude edit/write in each format; Codex
  evaluator is read-only; names match file names; Copilot `model` is a
  string; running the generator twice is idempotent.

## M18-002 — Review status, orchestrator step, evidence file

- FEATURES.json gains status `review` and optional fields `evaluate`
  (`"ui"` | `"none"`, default none), `bar` (a concrete, fetchable
  reference), `eval_attempts` (integer, orchestrator-owned).
- harness-session: a feature with `evaluate` set ends in `review`, not
  `passing`. SESSION line becomes
  `SESSION: <id> · <passing|review|blocked> · gate <green|red> · <commit|reason>`.
- harness-run dispatches the *named* agents `harness-builder` and
  `harness-evaluator` (neutral wording all three CLIs understand).
  After a `review` session: dispatch the evaluator on that commit, then
  verify the tree is clean and HEAD unchanged — any change rejects the
  verdict (Codex can re-apply parent overrides to children).
  - `PASS` → orchestrator writes `docs/verification/<id>.md` (verdict,
    findings, date, CLI), flips to `passing`, one PROGRESS.md line.
  - `NEEDS_WORK` → findings into `notes`, status back to `failing`,
    `eval_attempts` + 1; the next session starts from the findings.
  - `eval_attempts` reaches 2 → relay to the human, STOP.
- Security checklist applies when any `paths` entry matches the
  sensitive globs in `agents/models.json` (auth, payments, personal
  data, migrations) — default list, overridable per repo.
- Gate: test-session.sh fixtures for the new status and fields;
  status.sh treats `review` as not-done and never selects it as NEXT;
  absent fields keep today's behaviour exactly.

## M18-003 — Protocol, planning interview, audit; release 1.9.0

- Protocol §1.4 asks per feature: "Can the gate prove this? If not,
  what is the bar?" → `evaluate` / `bar`. §2.7 documents the review
  step and the evidence file. FEATURES.json.tmpl `_instructions`
  documents the status and fields.
- harness-setup and the harness-session upgrade offer run
  gen-agents.sh; harness-audit WARNs when opted-in features exist but
  agent files are missing, and suggests `evaluate: "ui"` for failing
  features whose verify is manual or UI-shaped (human approves).
- README lifecycle and skill list name the evaluator. Versions 1.9.0.

## Decision log

- 2026-09-27 — Evaluator is dispatched by the orchestrator, never inside
  the session it judges.
- 2026-09-27 — Opt-in per feature: an evaluation is a full agent run.
- 2026-09-28 — One evaluator with three modes (review / QA / security)
  instead of three agents: each agent run re-reads spec and diff, so
  three agents cost ~3x for mostly overlapping work. Split only if
  logged verdicts show one mode crowding out another. Owner confirmed
  one evaluator with a QA mode on 2026-09-28.
- 2026-09-28 — Portable by design: current docs confirm all three CLIs
  let a skill dispatch a named custom agent with its own context and
  model. The Claude-only "built-in subagent" wording is replaced by
  named agents generated per CLI from one source.
- 2026-09-28 — Evidence files (`docs/verification/<id>.md`) adopted from
  the daybook repo, where ChatGPT recorded browser proof unprompted.
- 2026-09-28 — Post-evaluator integrity check (clean tree, HEAD
  unchanged) because read-only is not reliably enforced in every CLI
  when the parent runs with elevated permissions.
