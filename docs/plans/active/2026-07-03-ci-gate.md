# CI Gate Enforcement Plan (Milestone 5)

**Goal:** Run `scripts/e2e.sh` in GitHub Actions on every push to `master`
and every pull request, so the gate is enforced mechanically, not by
discipline (spec §3 deferred item; OpenAI pillar: enforce invariants
mechanically).

**Scope:** One feature, M5-001. A single workflow file; no other CI concerns
(release automation, matrix builds) — YAGNI.

## Task 1: gate workflow (M5-001)

**Files:** Create `.github/workflows/gate.yml`

- [ ] Step 1: Write the workflow: checkout → `apt-get install jq shellcheck`
      → `bash scripts/e2e.sh`, triggered on `push` to `master` and on
      `pull_request`.
- [ ] Step 2: Run the gate locally (green), commit the workflow, push the
      branch — this opens the RED→GREEN cycle in CI itself: the Actions run
      on the branch is the failing-then-passing test.
- [ ] Step 3: Watch the Actions run for the branch (`gh run watch`); it must
      end green. If it fails, fix and push until green.
- [ ] Step 4: Only after the run is green: append M5-001 to FEATURES.json as
      `passing`, add the PROGRESS.md entry, commit, push.
- [ ] Step 5: Open the PR; its checks must show the gate green. Move this
      plan to `docs/plans/completed/`.

**Verify (M5-001):** the GitHub Actions "gate" workflow run for this branch
completes successfully (`gh run list --workflow=gate.yml` shows a green run
for the head SHA).

## Decision log

- 2026-07-03 — The FEATURES.json entry cannot land in the same commit as the
  workflow: its `verify` criterion is a green CI run, which only exists
  after a push. The entry therefore lands in the immediately following
  commit, after the proof — the "no standalone failing entries" rule is
  respected (the entry is born `passing`).
