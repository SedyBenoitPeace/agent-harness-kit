# M34: Run fixes — quick handoff, correct reports, cheaper runs

**Goal:** fix everything the M32/M33 runs (Claude Code) and the Codex runs on
the owner's iOS project exposed: a handoff that runs the full gate, run
reports that mix runs and misattribute decisions, models that step up for
the wrong reason, plans that ask builders for things only the owner can do,
a noisy supervisor, sequential runs where lanes were possible, and
orchestrators and builders that read far more than they need.

**Why now:** the handoff is blocking the owner's daily work on a repo whose
full gate runs simulator UI suites; the rest came out of the 2026-10-15 run
reports (docs/runs/2026-10-15-*.md) and the Codex session analysis.

## Before the run

Nothing. Every `verify` below is provable by a builder from this repo alone
(scripts, fixtures, tests). No live session, push, PR or owner answer is
needed; publishing the template mirror stays the owner's step after the run.

## M34-001 — Handoff reuses the last green gate (ASAP)

- `handoff.sh` stops running `bash scripts/e2e.sh` itself. It reads the
  green fingerprint `run-gate.sh` already records (M29-001):
  - tree identical (apart from PROGRESS.md and docs/plans/) to the last
    green gate → `GATE: green (last green run, unchanged)`, no test run;
  - otherwise → not blocked: `NOTE: gate not confirmed for the latest
    changes; the next session's baseline gate runs it`, and the generated
    prompt keeps "confirm the gate is green before starting";
  - `--run-gate` runs the full gate as today (red → BLOCKED);
  - `--skip-gate` keeps working, with the same wording as the NOTE.
- harness-handoff SKILL.md and the README describe the three cases.
- Verify: test-handoff.sh proves, without running a real gate (a stub
  `scripts/e2e.sh` that records it was called), that an unchanged tree
  hands off without calling the gate, a changed tree hands off with the
  NOTE and without calling it, `--run-gate` calls it and blocks on red.

## M34-002 — Each run starts with clean run state

- New `skills/harness-run/scripts/run-start.sh <repo>`: does
  harness-continuous Start step 2 deterministically: ignore rule for
  `.harness-run/`, writes `start`, empties `skip`, removes a stale `STOP`,
  and moves the previous run's `cost.log`, `run-cost`, `models.log`,
  `usage.log`, `budget.log` and `decisions/` into
  `.harness-run/previous/<old start commit>/` (kept, never deleted).
- harness-continuous SKILL.md Start calls it; run-report.sh then only ever
  sees the current run.
- Verify: test-run.sh proves a second run-start.sh moves every listed file
  of the first run into previous/<commit>/, leaves fresh `start` and empty
  `skip`, and that a report built after it shows only the second run.

## M34-003 — Decisions in the report belong to their feature

- run-report.sh takes each done feature's `Decisions:` from, in order: the
  feature's own commit message body (lanes put it there), then the
  PROGRESS.md entry whose `Done:` line names the id as done. An entry that
  only mentions the id (a planning session) never counts.
- Verify: test-run.sh fixture with a planning entry mentioning two ids, a
  lane commit carrying `Decisions:` in its body, and a normal session entry,
  proving each feature gets its own line and the planning text is never used.

## M34-004 — Claude Code edition: run-scoped ledger, right model, right step-up, quiet supervisor

- The hooks reset their in-memory cost split, budgets and pending usage
  when `.harness-run/start` changes, so a long session running several
  runs reports each run alone.
- Every builder start writes its models.log line, parallel lanes included
  (the "unknown" model in the 2026-10-15 reports); add a test with the
  exact lane prompt from harness-run's Parallel lanes step.
- Step-up counts only earlier starts made with the same feature `notes` as
  now: models.log records a short hash of the notes at each start, so an
  owner's answer (which changes the notes) gives a fresh attempt at the
  planned size instead of a bigger model.
- The done-check supervisor is off by default (`supervisor` option, true
  turns it on) and never judges a parallel-lane builder: a lane does not
  run the full gate and ends by handing back to the orchestrator, so the
  transcript tail it reads always looks incomplete.
- Verify: mod tests prove the reset on a new start, the lane prompt's
  models.log line, no step-up after a notes change (and step-up without
  one), supervisor off by default, on with the option, and never for a
  lane prompt.

## M34-005 — Plans only ask builders for what they can prove

- Protocol 1.4: `verify` must be provable by a builder from the repo alone.
  Anything needing a live session, the owner's machine, hardware, a push,
  a PR or an answer goes in the plan's `## Before the run` section, settled
  before the run, or in a step the owner does after it.
- harness-audit WARNs on a failing feature whose `verify` names such a
  thing (word list: real session, owner, machine, device, hardware, push,
  pull request, PR, ask, human, manually), and on an active plan whose
  features declare neither `depends_on` nor `paths` (no lanes possible).
- Verify: test-audit.sh proves both WARNs with fixtures and no WARN on this
  repo's M34 features; the protocol neutrality check stays green.

## M34-006 — Shared resources keep lanes apart

- Optional feature field `exclusive`: a resource name (`simulator`,
  `device`, `database`). context.sh never puts two features with the same
  `exclusive` value in one PARALLEL batch; everything else can still run
  in parallel. Protocol 1.4 and the FEATURES template name it; audit
  accepts it.
- Verify: test-session.sh (or the suite that covers context.sh) proves two
  independent features sharing `exclusive` are not batched together, a
  third without it still joins, and behaviour is unchanged without the
  field.

## M34-007 — Orchestrators wait once and read only script output

- Every builder's last act writes `.harness-run/results/<id>.txt`: its
  SESSION line and at most 10 lines of summary.
- New `skills/harness-run/scripts/wait-result.sh <id> [--timeout <s>]`
  blocks in the shell (not in the model) until that file exists, then
  prints it: one tool call per builder.
- harness-run and harness-continuous: dispatch, then one blocking wait per
  builder (the CLI's own blocking wait with its longest timeout, or
  wait-result.sh); never short polls, never `send_message` to steer a
  running builder; read only script output (`context.sh`, `status.sh`,
  results files), never SKILL.md, PROGRESS.md, FEATURES.json or plans
  whole; a run resumed later starts in a fresh conversation. Protocol 2.7
  says the same, agent-neutral.
- Verify: test-run.sh proves wait-result.sh returns the file as soon as it
  appears, exits non-zero on timeout, and makes no output while waiting;
  e2e.sh checks both skills and protocol 2.7 carry the rules and that no
  orchestrator step reads those files whole.

## M34-008 — Builders see summaries, not logs

- New `skills/harness-session/scripts/quiet.sh <name> -- <command…>`: runs
  any build or test command, keeps the full output in
  `.harness-run/logs/<name>-<time>.log`, and prints only the exit code, the
  log path, lines matching error/fail/warning patterns (max 40) and the last
  20 lines, each line cut to 300 characters.
- `run-gate.sh` prints the same shape (no long raw tails), and the session
  protocol tells builders to run every build, simulator and test command
  (`xcodebuild`, `simctl`, test runners) through `quiet.sh`, never raw, and
  to read a log only by searching it.
- Verify: test-session.sh proves quiet.sh's exit code passthrough, the log
  file, the 40-line and 300-character caps on a noisy fixture command, and
  run-gate.sh's capped output on a red stub gate.

## M34-009 — A short session brief instead of whole files

- `context.sh` prints a brief, not a history: the current milestone only
  (earlier ones as one line, e.g. `M0–M33 complete`), the NEXT feature's
  full entry (verify, notes, paths, model, effort), that feature's section
  of the active plan (by its heading), the newest PROGRESS.md entry and
  `git log --oneline -5`. Target: under 80 lines on any repo.
- Protocol section 2 and harness-session: the brief is the session's
  start; FEATURES.json, PROGRESS.md, ARCHITECTURE.md, PRODUCT.md and plans
  are read on demand with `grep` or `sed -n` ranges, never whole.
- Verify: test-session.sh on a fixture with 30 completed milestones proves
  the brief stays under 80 lines, lists only the current milestone, and
  contains NEXT's full entry, its plan section and only the newest PROGRESS
  entry; e2e.sh checks the protocol and skill carry the on-demand rule.

## M34-010 — Completed milestones leave FEATURES.json

- New `skills/harness-status/scripts/archive-features.sh`: moves every
  milestone whose features are all `passing` or `superseded` from
  FEATURES.json to `docs/features-archive.json` (same schema, appended).
- status.sh, context.sh, run-report.sh and harness-audit read archived ids
  where they need them: archived ids count as `passing` for `depends_on`,
  titles resolve for reports, and ids stay unique across both files.
- harness-continuous End runs it after the report; harness-session never.
- Verify: test-status.sh proves archiving moves only fully done milestones,
  a failing feature depending on an archived id is still eligible, the
  report still titles an archived id, and audit fails on an id present in
  both files.

## M34-011 — Sessions have a budget

- Protocol section 2: a builder that passes 60 tool calls, or whose context
  passes about 150k tokens, stops: commits what it has on its branch,
  appends a resume note to the feature's `notes`, and ends with
  `SESSION: <id> · blocked · gate <…> · session budget`.
- harness-run and harness-continuous treat `session budget` as "continue
  in a fresh session": one retry at the same size (the notes changed, so
  M34-004 gives no step-up), never a skip; a second budget stop is a skip.
- Claude Code edition: the hooks show a status-line notice at 80% of the
  budget, measured from the turn's context.
- Verify: e2e.sh checks the protocol rule and both skills' handling; mod
  tests prove the notice at 80% of a configured budget and none below it.

## M34-012 — Audit sees global plugins that fight the protocol

- harness-audit also reads the person's global CLI setup when it is
  readable: `~/.codex/config.toml` MCP servers, Claude Code settings'
  enabled plugins and MCP servers, `~/.copilot/mcp-config.json`. A memory or
  workflow server (name or command matching memory, engram, mem0,
  workflow) gets an informational WARN: it may inject its own instructions
  into every session of a harnessed repo. The audit never tells the person
  to change their setup.
- Never fails, never edits those files; `HARNESS_AUDIT_HOME` points it at
  another home for tests.
- Verify: test-audit.sh with a fixture home holding an engram server in a
  Codex config, a memory plugin in Claude settings, and a clean Copilot
  config proves exactly the two WARNs, and none with an empty home.

## Decision log

- 2026-10-15: one milestone (owner); M34-001 first, it blocks daily work.
- 2026-10-15: handoff never runs the full gate by default. A gate run on
  the same files is proof enough; on changed files the next session's
  baseline gate is where it runs anyway, so a handoff gate only added
  minutes and pushed people to `--skip-gate`, whose warning was then
  inherited by every later session.
- 2026-10-15: step-up resets when the feature's notes change: a skip for an
  owner question is not evidence the model was too small (M32-002 and
  M33-003 went to opus for that reason alone).
- 2026-10-15: supervisor off by default: across four runs it flagged every
  feature, lanes especially, so it caught nothing.
- 2026-10-15 (owner, from 30 Codex sessions on the iOS project, 13–15
  Oct: ~121M tokens, 96% cached; 97 wait_agent + 69 wait + 11 sleep + 103
  send_message calls; 139 raw xcodebuild/simctl calls vs 42 through
  run-gate.sh; 124 calls to a global memory server; whole-file reads of
  skills, AGENTS.md, FEATURES.json, ARCHITECTURE.md, PRODUCT.md every
  session; builders up to 118 calls and 211k context): the protocol already
  said "read only when needed" and "keep only a summary", but prose was not
  followed. M34 adds mechanisms (brief, result files, wrappers, budgets,
  archive, audit) instead of more prose.
- 2026-10-15: lessons from M32/M33 applied here: every verify is provable
  from the repo, every feature has depends_on and paths, so the run can use
  lanes.
- 2026-10-15 (owner): M34-012 names no third-party plugin (the hygiene grep
  stays as is, no pattern tricks around it) and its WARN only informs: the
  kit does not get a say on the person's own setup.
