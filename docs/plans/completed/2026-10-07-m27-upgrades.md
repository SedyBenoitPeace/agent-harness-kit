# M27: A clear upgrade every release, model fallback, a fuller run report

**Goal:** every kit release tells an existing repo exactly how to upgrade,
and one command does it; models degrade gracefully; the one page read after
an unattended run shows what the new signals found.

**Why:** the owner wants a clear upgrade process every time the harness is
updated. Gaps found before the first real run: upgraded repos kept stale
builder agents; models.json named retired models, and Copilot's "strong"
model was Claude, so a Copilot second opinion was the same vendor; the run
report ignored decisions, the supervisor and the budget guard; the template
mirror repo was last synced at M13.

## M27-001 — upgrade.sh refreshes every generated agent file

- When a repo has any generated harness agent file (any role, any CLI),
  upgrade.sh re-runs gen-agents.sh for it, so builder, evaluator and brief
  reviewer pick up new instructions; it prints `CHANGED:` per file that
  changed and `OK:` when none did. Fixture in test-upgrade.sh.

## M27-002 — Model rule of thumb and fallback

- models.json: Claude strong `opus` (complex work), standard `sonnet`
  (implementation); Codex strong `gpt-6-astra`, standard `gpt-6.1-sol`;
  Copilot strong `gpt-6-astra` (a second vendor next to a Claude builder),
  standard `claude-sonnet-5.5`. `_instructions` states the rule.
- A model value `auto` (or missing) means "let the CLI choose": gen-agents
  writes no model line, second-opinion.sh passes no model flag.
- second-opinion.sh: when the CLI rejects the model (non-zero exit, empty
  reply, an error naming the model), it retries once without a model flag
  and prints `MODEL: <name> unavailable, <cli> chose its own`.
- harness-run: a named agent that fails to start because its model is
  unavailable is replaced by the CLI's own built-in subagent for that
  dispatch, and the run report says so.

## M27-003 — Run report shows decisions, supervisor and budget

- run-report.sh: under each done feature, its PROGRESS.md `Decisions:` line;
  a "Supervisor" section listing `.harness-run/decisions/<id>.skipped.md`
  items; a "Budget" section from `.harness-run/budget.log`. Absent files,
  absent sections. Fixtures in test-run.sh.

## M27-004 — A clear upgrade process for every release

- `CHANGELOG.md`: one entry per release, newest first, each with an
  "Upgrade:" block saying what an existing repo must do (or "nothing beyond
  the standard upgrade"). The gate fails when the current version has no
  entry.
- upgrade.sh records the kit version it upgraded to in
  `docs/agents/harness-kit-version` and prints the CHANGELOG "Upgrade:"
  notes for every release newer than the recorded one (all of them when
  none is recorded).
- README "Upgrading after every release": update plugins, branch, run
  harness-upgrade-structure, read the printed notes, harness-audit, gate,
  commit, PR. harness-upgrade-structure SKILL.md relays the notes.

## M27-005 — Template mirror sync; release 3.5.0

  the mirror's layout (keeping the mirror's own banner, README and
  docs/PRODUCT.md), or with `--check` exits 1 when the mirror is behind.
  Fixture in its own test. Release checklist in CHANGELOG.md says to run it.
