# M53: acceptance checks, phase 1 of the zero-touch QA chain

Decisions: `docs/decisions.md` (2026-11-20). Every feature of this milestone
carries its own `checks`, and `scripts/test-checks.sh` names one test per
check id, so the kit dogfoods the format it ships.

## Check format

FEATURES.json, per feature:

    "checks": [{"id": "M53-001.1", "title": "…", "critical": true,
                "steps": ["…"], "pass_if": "…", "evidence": "test"}]

Markdown (a GitHub issue body, a brief's `## Checks` section):

    ### M53-001.1 — title
    - **Critical:** yes
    - **Steps:**
      1. …
    - **Pass if:** …
    - **Evidence:** test

`evidence` is `test`, `screenshot` or `human`. Ids are `<feature id>.<n>`
(a brief, written before features exist, uses `C<n>`). Unknown fields
(`Accounts`) are ignored. Every check, whatever its evidence, has exactly
one test whose title starts with the id; `@critical` in the title iff
`critical`.

## M53-001 reader

`skills/harness-session/scripts/read-checks.sh`: prints one JSON line per
check, `{feature, id, title, critical, steps, pass_if, evidence}`.
Backends: FEATURES.json (default), `--issue-json FILE` (the output of
`gh issue view N --json number,title,body`), `--issue N` (calls `gh`),
`--md FILE`. Problems go to stderr, one per line, exit 1.

## M53-002 brief

Brief template gets `## Checks`; check-brief.sh FAILs when it has no check,
a check is malformed, or a Pass if is vague (a word list: works, correctly,
properly, as expected, fine, good, nice, appropriate). The reviewer lists
missing or vague checks as BLOCKING.

## M53-003 builder

harness-builder: one test per check, written first, titled with the id
(`@critical` when critical).

## M53-004 coverage

`skills/harness-session/scripts/check-coverage.sh DIR...`: for features
`passing` or `review`, every check has exactly one test and the critical
tag agrees; any test naming an unknown check id fails. Setup installs it
and the reader into `scripts/`; `e2e.sh.tmpl` runs it. This repo's gate
runs it over `scripts/test-checks.sh` (the fixtures hold ids of a demo
feature list). Ceiling: coverage is textual, so a `test.todo` or a string
with the id counts; the evaluator's per-check table catches stubs.

## M53-005 evaluator verdict

The evaluator writes one table row per check (`covered | partial |
missing | unrequested`) and runs `acceptance-verdict.sh <id> <table>`;
PASS only when every check has exactly one row and every row is
`covered`. The script decides.
